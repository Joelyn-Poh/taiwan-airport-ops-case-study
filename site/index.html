桃園機場旅客叫車優惠分析

從雜亂的叫車資料，找到可以執行的答案

發優惠真的能讓更多旅客叫車嗎？增加的行程，是否值得付出優惠成本？

一句話結論 活動有效，
但先不要全面推出。

行程增加了，但優惠成本、預算與機場等車時間都沒有通過標準。

  1. 01想問題優惠是否值得？
  2. 02整理資料先排除無效紀錄
  3. 03比較方案用 Control 當基準
  4. 04做決定效果、成本、服務一起看

本專題使用合成資料，不代表任何真實叫車平台，也未使用公司的內部資料。

01

專題構想

為什麼選擇這個題目？

我把自己設定成叫車平台的營運分析人員，模擬平台和旅遊業者合作，向抵達桃園機場的旅客發送叫車優惠。

一般活動報告常只回答「訂單有沒有增加」，但這還不夠。如果活動讓訂單變多，卻同時造成虧損、超支或等車時間變長，平台仍然不應該直接擴大活動。

問題 A有沒有效？

優惠組是否比沒有優惠的 Control 組多出完成行程？

問題 B有沒有賺？

新增收益是否足以支付優惠成本？

問題 C現場接得住嗎？

司機供給、接車時間與取消率是否仍在合理範圍？

假設情境

旅遊合作夥伴提供即將抵達桃園機場的旅客資料，平台在旅客抵達前透過 CRM（顧客訊息管理系統）發送訊息，並追蹤抵達後七天內的叫車行為。

03

資料設計

為什麼要故意放進錯誤資料？

實際叫車資料會來自乘客 App、司機端、付款系統、CRM 與合作夥伴。不同系統可能重複傳送、延遲到達，或缺少欄位。

如果專題資料全部都很乾淨，就無法展示資料清理工作。因此，我刻意把常見問題混進合成資料，再用 SQL 找出、分類並處理。

raw_trip_orders

raw_trip_events

行程各階段的事件時間

raw_payments

付款與退款紀錄

raw_campaign_assignments

活動分組結果

raw_promo_redemptions

優惠使用紀錄

raw_crm_events

訊息發送、開啟與點擊

raw_supply_hourly

每區每小時的需求與司機數

刻意加入的無效資料

  • 同一筆訂單或事件被重複傳送
  • 時間格式無法讀取，或事件時間出現在未來
  • 完成時間早於上車時間
  • 座標為空值、0,0，或不在台灣範圍
  • 訂單找不到對應乘客或司機
  • 車資為負數，或付款高於車資
  • 優惠使用者和叫車使用者不同
  • Control 組出現優惠使用紀錄
  • 事件延遲一天以上才進入系統
04

推演過程

我怎麼從原始資料走到結論？

  1. Step 01

    保留原始資料

    CSV 完整讀進 raw_* 原始資料層，不直接修改，方便日後回頭查證。

  2. Step 02

    統一資料格式

    移除多餘空白，把狀態改成統一小寫，並將時間、座標與金額轉成正確格式。

  3. Step 03

    處理重複資料

    同一個 trip_id 只保留最早收到的一筆；其他資料標記為重複，不直接刪除。

  4. Step 04

    檢查資料是否合理

    依序檢查事件時間、事件順序、座標、乘客與司機、車資、付款及優惠資格。

  5. Step 05

    重建每一趟行程

    用事件資料重新整理 requested → accepted → picked_up → completed，不直接相信訂單最後狀態。

  6. Step 06

    找出活動分析對象

    保留有確認抵台訂位、同意 CRM、不在風險名單，而且活動前 180 天沒有台灣完成行程的旅客。

  7. Step 07

    比較三個組別

    比較訊息互動、機場完成率、七天內再次叫車率、優惠成本及額外貢獻。

  8. Step 08

    檢查營運狀況

    一起檢查每區每小時的接單率、取消率、接車時間、司機供給及每日預算。

06

結論建議

暫不全面推出，先修改方案

最後判斷 活動有效
≠ 適合擴大
  1. 兩種方案的額外貢獻都是負數。
  2. 活動支出達預算的 139.3%。
  3. 桃園機場接車時間超過設定上限。

我會怎麼改善？

  1. 01
    繼續保留 Control

    確認沒有優惠時的自然叫車率，避免把本來就會發生的行程算成活動成果。

  2. 02
    優先修改 Bundle

    降低第二趟優惠金額、設定最低車資，或和旅遊合作夥伴共同負擔成本。

  3. 03
    分批發送 CRM

    依機場每小時的司機供給決定發送人數，不一次把所有需求推進市場。

  4. 04
    設置自動停止條件

    當接車時間、取消率或預算超標時，暫停新的訊息發送。

專題限制

  • 所有資料均為合成資料，不能代表任何真實叫車平台的營運結果。
  • 沒有納入天氣、航班延誤、其他交通工具或競爭平台價格。
  • 沒有真實合作夥伴成本及客服案件資料。
  • 分析期間只有八週，無法判斷更長期留存。
07

SQL 指令章節

每一步用了哪些表格與指令？

這個專題使用 DuckDB SQL。以下依實際順序說明每一步的輸入資料表、輸出資料表、主要指令，以及為什麼要這樣算。

CSV→raw_*→stg_*→fct_trip_lifecycle→mart_*

raw_* 是原始資料層；stg_* 是完成格式統一的暫存層；fct_* 是每趟可信行程；mart_* 是提供報告與決策使用的彙整表。

01
讀取原始 CSVCSV → raw_trip_orders

先把所有欄位當文字讀入，避免錯誤日期或金額讓整個匯入中斷。

CREATE OR REPLACE TABLE raw_trip_orders AS
SELECT *
FROM read_csv_auto(
  'data/raw_sample/raw_trip_orders.csv',
  header = true,
  all_varchar = true
);
查看完整 SQL
02
統一欄位格式raw_trip_orders → stg_trip_orders

trim 移除空白、lower 統一狀態、try_cast 轉換時間與數字；轉換失敗時先留下空值。

SELECT
  trim(trip_id) AS trip_id,
  trim(user_id) AS user_id,
  try_cast(requested_at AS TIMESTAMPTZ) AS requested_at,
  try_cast(pickup_lat AS DOUBLE) AS pickup_lat,
  try_cast(gross_fare_twd AS DOUBLE) AS gross_fare_twd,
  lower(trim(terminal_status)) AS terminal_status
FROM raw_trip_orders;
查看完整 SQL
03
找出重複訂單stg_trip_orders → stg_trip_orders_dedup

把相同 trip_id 放在一起，依收到時間編號。第一筆保留，其他標記為重複。

row_number() OVER (
  PARTITION BY trip_id
  ORDER BY ingested_at
) AS row_num
查看完整 SQL
04
檢查座標、車資與付款訂單＋付款 → trip_quality_issues

先用 WHERE 找出空座標或不在台灣範圍的行程；再用 JOIN 連接付款，檢查負車資或付款高於車資。

WHERE pickup_lat IS NULL
   OR pickup_lng IS NULL
   OR pickup_lat NOT BETWEEN 21.5 AND 25.5
   OR pickup_lng NOT BETWEEN 119.0 AND 122.5;

SELECT o.trip_id, sum(p.amount_twd) AS payment_twd
FROM stg_trip_orders_dedup o
JOIN stg_payments p ON o.trip_id = p.trip_id
GROUP BY o.trip_id, o.gross_fare_twd
HAVING o.gross_fare_twd < 0
    OR sum(p.amount_twd) > o.gross_fare_twd;
查看完整 SQL
05
重建行程事件順序stg_trip_events_dedup → fct_trip_lifecycle

同一趟行程原本有多筆事件，先整理成一列，再檢查時間是否依序前進。

SELECT
  trip_id,
  min(event_at) FILTER (WHERE event_type = 'requested') AS requested_at,
  min(event_at) FILTER (WHERE event_type = 'accepted') AS accepted_at,
  min(event_at) FILTER (WHERE event_type = 'picked_up') AS picked_up_at,
  min(event_at) FILTER (WHERE event_type = 'completed') AS completed_at
FROM stg_trip_events_dedup
GROUP BY trip_id;
查看完整 SQL
06
找出活動旅客活動分組＋訂位＋CRM＋行程 → mart_campaign_cohort

EXISTS 確認旅客收到 CRM；NOT EXISTS 排除活動前 180 天已完成台灣行程的人。

AND EXISTS (
  SELECT 1 FROM stg_crm_events crm
  WHERE crm.user_id = a.user_id
    AND crm.crm_event_type = 'sent'
    AND crm.event_at BETWEEN a.assigned_at AND b.arrival_at
)
AND NOT EXISTS (
  SELECT 1 FROM fct_trip_lifecycle f
  WHERE f.user_id = a.user_id
    AND f.valid_for_trip_kpi
    AND f.lifecycle_status = 'completed'
    AND f.requested_at >= a.assigned_at - INTERVAL '180 days'
    AND f.requested_at < a.assigned_at
);
查看完整 SQL
07
計算活動漏斗活動旅客＋CRM＋行程 → mart_campaign_funnel

用 COUNT FILTER 在同一份查詢中計算分組、收到訊息、開啟、叫車與完成行程的人數。

SELECT
  experiment_arm,
  count(*) AS assigned_users,
  count(*) FILTER (WHERE crm_sent) AS crm_sent_users,
  count(*) FILTER (WHERE airport_requested) AS request_users,
  count(*) FILTER (WHERE airport_completed) AS completed_users
FROM campaign_users
GROUP BY experiment_arm;
查看完整 SQL
08
計算完成率與活動增量int_campaign_user → mart_experiment_results

先算每組完成率，再減去 Control 完成率。差值乘上優惠組人數，就是估計增加的完成行程。

g.airport_completed_users::DOUBLE
  / nullif(g.assigned_users, 0) - c.p0
  AS incremental_conversion_rate,

(g.airport_completed_users::DOUBLE
  / nullif(g.assigned_users, 0) - c.p0)
  * g.assigned_users
  AS incremental_completed_trips
查看完整 SQL
09
計算每區每小時服務品質可信行程＋司機供給 → mart_marketplace_hourly

date_trunc 將資料整理成每小時，quantile_cont 計算 P90 接車時間。

SELECT
  date_trunc('hour', requested_at) AS snapshot_hour,
  origin_zone AS service_zone,
  count(*) AS requests,
  quantile_cont(pickup_eta_min, 0.90)
    FILTER (WHERE lifecycle_status = 'completed') AS p90_eta
FROM fct_trip_lifecycle
WHERE valid_for_trip_kpi
GROUP BY 1, 2;
查看完整 SQL
10
計算每日累積預算有效優惠 → mart_campaign_budget_daily

SUM OVER 依日期累加支出，再用 CASE WHEN 分成正常、花太快與超過預算。

sum(daily_spend_twd) OVER (
  ORDER BY campaign_date
) AS cumulative_spend_twd,
CASE
  WHEN cumulative_spend_twd > 150000 THEN 'alert_over_budget'
  WHEN cumulative_spend_twd > planned_spend_twd * 1.15 THEN 'alert_over_pace'
  ELSE 'on_track'
END AS budget_status
查看完整 SQL

專題心得

我從這份專題學到什麼？

資料分析不是把資料放進圖表就結束。分析以前要先確認資料是否可信；活動訂單增加後，還要一起檢查成本、預算及服務品質。

SQL 在這個專題中不只是計算工具，也負責記錄每一步規則。別人可以沿著相同的資料表和指令，檢查我的分析是否合理。

最重要的學習是：活動有效，不代表適合全面推出。
